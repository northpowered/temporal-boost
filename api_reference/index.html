API Reference

Complete API reference for Temporal-boost.

BoostApp

Main application class for Temporal-boost.

BoostApp.__init__()

Initialize a BoostApp instance.

BoostApp(
    name: str | None = None,
    *,
    temporal_endpoint: str | None = None,
    temporal_namespace: str | None = None,
    debug_mode: bool = False,
    use_pydantic: bool | None = None,
    logger_config: dict[str, Any] | str | Path | None = DEFAULT_LOGGING_CONFIG,
    shutdown_timeout: float = 30.0,
) -> None

Parameters:

  • name (str | None): Application name. Defaults to "temporal_generic_service".
  • temporal_endpoint (str | None): Override TEMPORAL_TARGET_HOST environment variable.
  • temporal_namespace (str | None): Override TEMPORAL_NAMESPACE environment variable.
  • debug_mode (bool): Enable debug mode. Defaults to False.
  • use_pydantic (bool | None): None inherits TEMPORAL_USE_PYDANTIC_DATA_CONVERTER; True enables Pydantic and False disables automatic Pydantic selection. An explicit client data_converter takes priority.
  • logger_config (dict | str | Path | None): Logging configuration. Can be a dict, path to JSON/YAML file, or path to logging config file.
  • shutdown_timeout (float): Shared timeout in seconds for cooperative shutdown and joining worker threads. Must be finite and non-negative. Independent of Temporal SDK configuration.

Example:

app = BoostApp(
    name="my-service",
    temporal_endpoint="localhost:7233",
    temporal_namespace="default",
    use_pydantic=True,
)

BoostApp.add_worker()

Add a Temporal worker to the application.

add_worker(
    worker_name: str,
    task_queue: str,
    *,
    activities: list[Callable[..., Any]] | None = None,
    workflows: list[type] | None = None,
    interceptors: list[Interceptor] | None = None,
    cron_schedule: str | None = None,
    cron_runner: MethodAsyncNoParam[Any, Any] | None = None,
    cron_workflow_id: str | None = None,
    **worker_kwargs: Any,
) -> TemporalBoostWorker

Parameters:

  • worker_name (str): Unique worker name. Cannot be reserved names: "run", "cron", "exec", "all".
  • task_queue (str): Temporal task queue name.
  • activities (list[Callable] | None): List of activity functions.
  • workflows (list[type] | None): List of workflow classes.
  • interceptors (list[Interceptor] | None): List of Temporal interceptors.
  • cron_schedule (str | None): CRON schedule string for scheduled workflows.
  • cron_runner (MethodAsyncNoParam | None): Workflow run method for CRON workers.
  • cron_workflow_id (str | None): Stable workflow ID in the configured namespace. Defaults to temporal-boost/cron/<percent-encoded task_queue>/<percent-encoded worker_name>. Empty or whitespace-only explicit IDs raise ValueError.
  • **worker_kwargs: Additional worker configuration options.

cron_schedule and cron_runner must be provided together or both omitted. Partial configuration, or an explicitly empty/whitespace-only schedule, raises ValueError during worker construction before connecting. Expression syntax is validated by the SDK/server. These rules also apply to direct TemporalBoostWorker construction. Supplying cron_workflow_id alone does not enable CRON mode. add_worker() registers commands locally; it does not create a server-side schedule.

graceful_shutdown_timeout=timedelta(...) in worker_kwargs sets the SDK activity grace period. Omission or None inherits TEMPORAL_GRACEFUL_SHUTDOWN_TIMEOUT (default 30 seconds), zero is preserved, and negative durations raise ValueError at registration. This is independent of BoostApp.shutdown_timeout; see configuration.

Returns:

  • TemporalBoostWorker: The created worker instance.

Example:

worker = app.add_worker(
    "my_worker",
    "my_queue",
    activities=[my_activity],
    workflows=[MyWorkflow],
)

BoostApp.run()

Run the application CLI.

run(args: list[str] | None = None, **kwargs: Any) -> Any

args is one list of CLI arguments. Omission or None uses sys.argv[1:]; [] stays empty and triggers the configured no-command help/usage behavior (code 2). Separate positional arguments and a single command string are unsupported: use app.run(["run", "worker_name"]).

By default Typer raises SystemExit: help and successful commands use 0; unknown commands, missing arguments, and invalid values use 2. Explicit nonzero exits are preserved. Unhandled worker errors propagate and produce a nonzero process status. In run all, a worker's SystemExit(0) or SystemExit(None) is converted to RuntimeError at the CLI boundary so coordinator failure cannot report success; a direct run_all_workers() still raises the original exception.

Options such as standalone_mode=False and prog_name="service" are forwarded to Typer. In non-standalone mode, run() returns the command's value and propagates parsing/worker exceptions (for example, click.UsageError or RuntimeError). Help returns 0. Explicit callback exits follow Typer's semantics: a SystemExit raised directly by a callback still propagates. The return value is not a general exit-status API; use the default standalone mode at a process entry point.

Example:

if __name__ == "__main__":
    app.run()

For embedding, call app.run(["exec", "check"], standalone_mode=False) after registering check. Migration: callers that previously relied on run() swallowing SystemExit must now catch it explicitly or choose non-standalone mode and handle exceptions.

BoostApp.run_all_workers() and BoostApp.stop()

run_all_workers() -> None
stop() -> None

run_all_workers() starts a thread for each registered worker and waits for a stop request or failure. In the main thread it temporarily handles SIGINT and SIGTERM. stop() requests shutdown from any thread, returns immediately, and is safe to repeat. Calls outside a run do not affect the next run. Once stopping, the coordinator calls each live worker's request_stop() and joins all threads within shutdown_timeout. It raises TimeoutError naming any remaining workers if there was no earlier failure. Otherwise the timeout is logged and the earlier exception is re-raised. Their daemon threads may continue; restarting is rejected while they remain alive. Concurrent calls are rejected too.

The first worker failure requests application shutdown and is re-raised with its original traceback after cleanup. Later failures are logged without replacing it. A normal run() return before application shutdown is a RuntimeError; finite workers must call app.stop() before returning or use an individual command. A normal return or asyncio.CancelledError / concurrent.futures.CancelledError during application shutdown is accepted. Cancellation before stop and all other exceptions (including SystemExit / KeyboardInterrupt) propagate as failures. The same ordering preserves startup and stop-request failures. The CLI converts a failure with a success SystemExit code as described above. The external multi-process supervisor propagates the first observed child failure after stopping its peers.

Workers must opt into managed stopping. TemporalBoostWorker supports this contract; FastStream and ASGI adapter integration remains pending. See Graceful Shutdown for guarantees and limitations.

CLI Process Runner

The external launcher supports --workers N --shutdown-timeout SECONDS before the application path. The shutdown timeout applies when --workers > 1, defaults to 30 seconds, and must be finite and non-negative.

from temporal_boost.cli.process_runner import run_multiprocess

run_multiprocess(
    app_path: str,
    number_of_processes: int,
    arguments: list[str],
    *,
    shutdown_timeout: float = 30.0,
) -> None

Starts the same application command in each child. It observes every child independently, stops peers on the first nonzero child exit, joins terminated children, and closes process handles. No automatic restart occurs. Ordinary completion returns None once all children succeed. Failure raises SystemExit with the first observed positive child status; signal termination -N maps to 128 + N. Startup/cleanup exceptions propagate without replacing an earlier failure. A failure carrying SystemExit(0) or SystemExit(None) becomes RuntimeError. Invalid process counts or timeout values raise ValueError before processes are created.

The parent first requests managed stopping through dedicated one-way pipes and child watchers, then closes the stop endpoints. One grace deadline covers all children, followed by terminate (up to 5 seconds) and kill (up to 5 seconds). Main-thread invocation temporarily handles SIGINT/SIGTERM and restores the previous handlers; after cleanup the parent exits with 130/143 unless a failure determined the result. Repeated signals keep the first request and its deadlines. This timeout is independent of the application and SDK budgets. See Multi-process Supervision for command examples, managed worker requirements, and migration.

Worker Stop Contract

BaseBoostWorker.request_stop() -> bool is a non-blocking, thread-safe stop request. Implementations must tolerate repeats and requests during startup. Return True when supported; the default returns False. Async cleanup belongs on the resource-owning loop.

AsyncBoostWorker (exported from temporal_boost and temporal_boost.workers) provides this contract for asyncio workers. Call super().__init__(), set name, implement async run_async() and shutdown(), and inherit run() and request_stop(). The helper owns the loop, runs shutdown() once per run, and waits for run_async() to return. shutdown() must handle partial startup and unblock run_async(). If run_async() fails, its exception survives a subsequent cleanup failure, which is logged. When run_async() is cancelled and cleanup fails, the cleanup error propagates so normal cancellation cannot hide failed cleanup. See the example.

TemporalBoostWorker.run()

run() -> None

Example:

worker.run()

TemporalBoostWorker.cron()

Run the worker as a CRON worker.

Available as cron <name> only when both CRON parameters are configured. Calling this method directly without them raises RuntimeError before creating a loop or connecting. It registers once per process start, then keeps consuming the task queue until stopped.

Atomically starts or reuses the ID using WorkflowIDConflictPolicy.USE_EXISTING. Closed IDs are rejected with WorkflowAlreadyStartedError using WorkflowIDReusePolicy.REJECT_DUPLICATE, subject to server history retention. Reuse preserves the existing schedule and configuration. Local shutdown does not cancel the server-side workflow. See CRON identity and the UUID migration procedure.

cron() -> None

Example:

worker.cron()

Both commands own their event loop and use one lifecycle for startup, execution, and cleanup. A stop during startup cancels pending connection work. CRON cleanup completes the local wait and cancels any pending registration call, then stops the SDK worker. The adapter owns the SDK run() task and uses its public shutdown() API; it does not also enter the SDK async context manager. Normal run() does not register a CRON workflow. Local stop does not delete a server-side workflow.

Sequential runs are supported and rebuild the client, runtime, and SDK worker on the next loop. Concurrent run() / cron() calls on the same adapter raise RuntimeError. Startup and execution errors propagate after cleanup; later cleanup errors are logged without replacing the original error. Unexpected cancellation now propagates too. SDK validation failure before starting does not wait on an SDK shutdown() that could never finish. No public Client/Runtime close API exists in the supported SDK: the adapter releases its and its builders' references, and does not close caller-supplied executors or invent close methods. External references may keep SDK objects alive.

TemporalBoostWorker.request_stop() and TemporalBoostWorker.shutdown()

def request_stop() -> bool
async def shutdown() -> None

request_stop() returns True and requests stop without waiting, from any thread. Repeats are safe; a request before the first run is remembered and prevents resource creation. Requests after stopping have no effect on the next run. shutdown() before/after a run is a no-op. During a run it must be called on the owning loop, requests stop, and waits for lifecycle completion, including any error. Concurrent waiters share cleanup; cancelling a waiter does not cancel the lifecycle. A foreign-loop call raises RuntimeError directing callers to request_stop(). Use request_stop() inside worker callbacks too.

SDK shutdown is invoked at most once for an active SDK run. After SDK run() has already completed, its result is retrieved without another SDK shutdown call. On a shutdown failure the adapter cancels and joins its SDK task before releasing references. A stuck SDK operation can still exceed its activity grace period; BoostApp.shutdown_timeout bounds the coordinator's wait, not the SDK operation itself.

Lifecycle states

The read-only state property reports:

Value Meaning
created Constructed; no active lifecycle
building Creating runtime, connecting client, and constructing the SDK worker
running SDK run task started; CRON registration may still be pending
stopping Cancelling startup/CRON work and waiting for SDK cleanup
stopped Adapter and builder resource references released; another run is allowed

Early stop or failure may skip running. Setup options should be configured before a run.

Properties

  • temporal_client (Client): Get Temporal client instance.
  • temporal_worker (Worker): Get Temporal worker instance.
  • temporal_cron_runner (MethodAsyncNoParam): Get CRON runner method.
  • cron_workflow_id (str): Read-only resolved CRON workflow ID.
  • state: Current lifecycle state. Client and SDK worker properties raise after cleanup until rebuilt.

TemporalWorkerBuilder.build()

Build and return Temporal worker.

def build() -> Worker

Returns:

  • Worker: Temporal worker instance.

The builder passes graceful_shutdown_timeout directly to the SDK Worker. An explicit non-negative datetime.timedelta, including zero, overrides the environment; omission or None uses config.GRACEFUL_SHUTDOWN_TIMEOUT (30 seconds by default). A selected negative value raises ValueError when constructing the builder. BoostApp.add_worker() and TemporalBoostWorker forward this option through their worker kwargs without duplicating it.

This grace period begins when SDK shutdown is requested and controls how long activities may finish before cancellation is requested. It does not cap total SDK shutdown time, initiate application stop, or change application/process shutdown budgets. Workers omitting this option now receive the framework default instead of the SDK's zero grace period.

Configuration Constants

All configuration is available in temporal_boost.temporal.config:

  • TARGET_HOST: Temporal server address
  • CLIENT_NAMESPACE: Temporal namespace
  • CLIENT_TLS: TLS enabled flag
  • CLIENT_API_KEY: API key
  • CLIENT_IDENTITY: Client identity
  • USE_PYDANTIC_DATA_CONVERTER: Pydantic converter flag
  • MAX_CONCURRENT_WORKFLOW_TASKS: Max concurrent workflow tasks
  • MAX_CONCURRENT_ACTIVITIES: Max concurrent activities
  • MAX_CONCURRENT_LOCAL_ACTIVITIES: Max concurrent local activities
  • MAX_WORKFLOW_TASK_POLLS: Max workflow task polls
  • MAX_ACTIVITY_TASK_POLLS: Max activity task polls
  • NONSTICKY_STICKY_RATIO: Non-sticky to sticky ratio
  • GRACEFUL_SHUTDOWN_TIMEOUT: SDK activity grace period (timedelta, default 30 seconds), independent of application shutdown budget
  • PROMETHEUS_BIND_ADDRESS: Prometheus bind address
  • PROMETHEUS_COUNTERS_TOTAL_SUFFIX: Counters total suffix flag
  • PROMETHEUS_UNIT_SUFFIX: Unit suffix flag
  • PROMETHEUS_DURATIONS_AS_SECONDS: Durations as seconds flag

For detailed configuration options, see Configuration Guide.
